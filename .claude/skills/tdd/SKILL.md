# TDD：先寫考題，再寫答案

> 來源：以 Superpowers（obra/superpowers）的 test-driven-development 為骨架，改寫成繁體中文，
> 並調整為「導入進行中的專案」（2026-09-29 導入龍安專案）。專案的測試指令、測試位置、
> 哪些改動走 TDD、測不到的部分，寫在專案的 `CLAUDE.md`「測試（TDD）」段落。

## 核心觀念

先把「怎樣才算對」寫成可以重複執行的測試，再寫程式。

**一定要先看到測試失敗。** 沒失敗過的測試，就像上下限設成 0~200 dB 的測站，什麼都 PASS，等於沒把關。先看到它因為「功能還不存在」而失敗，才證明它真的抓得到錯。

TDD 本身不會自動找出 bug。它的價值在於：
- 寫測試時被迫把各種情況想清楚，很多 bug 在這一步就被想到。
- 之後每次修改，全部測試重跑，只要有一條由通過變失敗，就知道剛才改壞了東西。
- 修過的 bug 會留下一條測試，同樣的錯不會再回來。

## 開始前：讀專案說明、判斷要不要走 TDD、建立基準線

1. **讀專案說明**（CLAUDE.md、DEVELOPMENT.md、tests/README.md 等），找出：
   - 怎麼跑測試（指令）、目前的基準數字
   - 測試放哪裡、怎麼命名、有沒有共用的測試框架或輔助函式
   - **哪些改動要走 TDD、哪些不用**
   - 哪些東西測不到（例如畫面渲染、試算表格式、硬體量測）
   - 永遠要成立的規則（不變條件）

   找不到就問使用者，不要自己猜測試指令。

2. **判斷這次的改動要不要走 TDD。** 照專案說明的範圍判斷；不在範圍內的，照一般方式做，並在開始時說一聲「這部分不走 TDD，原因是……」。

3. **把現有測試全部跑一遍。**
   - 全部通過：記下數量（例如「136/136 通過」），這是基準線。
   - 有失敗：**先停下來回報**，列出失敗的測試名稱，不要動手修改。否則之後分不清是舊問題還是新改動造成的。
   - 專案完全沒有測試：先照下面「既有程式的處理」寫特徵測試。

## 主流程

### 步驟 1：列測試清單，先給使用者確認

動手寫程式前，用下面五種思考方式列出這次要測的情況，一條一句話，交給使用者確認。使用者看過清單，就等於先審過規格；漏掉的情況在這一步最便宜補上。

| 思考方式 | 要問的問題 | 例子 |
|---|---|---|
| 邊界值 | 「剛好」的地方對嗎？ | 規則「至少 9 人」→ 測 8、9、10 人 |
| 分類 | 輸入可分成哪幾類？每類至少一條 | 一般九人／全場 DH／DH 中途取消 |
| 異常輸入 | 空的、錯的、不合理的會怎樣？ | 沒填對手、名單空白、守位重複、後端回傳失敗 |
| 狀態順序 | 換個操作順序，結果還對嗎？ | 換投後重新整理，草稿還在嗎？ |
| 不變條件 | 什麼事無論如何都必須成立？ | 先發投手剛好 1 位 |

- **專案已經有「先問需求、整理規格、使用者回『開工』才動手」的流程時，測試清單直接放進規格摘要**，不要另外再審一次。使用者回「開工」，就同時批准了規格和測試清單。
- 修 bug 時，清單的第一條就是「重現這個 bug」。

### 步驟 2：紅燈，寫一條測試並看它失敗

- 一次只寫一條，只測一件事。測試名稱直接說出期望的行為，例如「出席 8 人：不能進入步驟二」。
- **期望值要用手算的常數**，或來自程式以外的可信來源（例如人工確認過的賽事戰報），不能用被測程式本身算出來，否則程式怎麼錯兩邊都會相等。
- 執行它，確認：
  - 它**失敗**了。一跑就通過，代表它測的是已經存在的行為，要改測試。
  - 失敗的**原因正確**：是因為功能還不存在，不是打錯字、路徑錯、import 失敗。原因不對就修正測試，直到它為了對的理由失敗。

如果發現邏輯根本測不到（例如判斷寫在 HTML 按鈕的 `:disabled`、`v-if` 裡），代表要先把它搬進程式邏輯變成可呼叫的函式。**不好測，通常代表設計可以更清楚。**

### 步驟 3：綠燈，寫最少的程式讓它通過

- 只寫讓這條測試通過所需的程式，不多加功能、不順手重構別的地方。
- 執行這條測試，確認通過。
- **再把全部測試跑一次**，和基準線比對。有任何一條原本通過、現在失敗，現在就修，不留到之後。
- 測試失敗時，修程式，不是改測試去遷就程式。

### 步驟 4：整理

測試全綠之後才整理：去除重複、改清楚的名稱、抽出共用函式。整理後再跑全部測試，必須維持全綠，而且不能新增行為。

### 步驟 5：下一條

回到步驟 2，處理清單的下一條，直到清單做完。

## 修 bug 的固定做法

使用者回報 bug 時，或自己在實測中發現 bug 時，一律：
1. 先寫一條重現它的測試，執行並回報它失敗。
2. 修程式，看它通過。
3. 全部測試重跑。

測試名稱可以標註來源，例如「【修正】DH 被代打後不算取消 DH」，之後回頭看就知道這條測試為什麼存在。

## 既有程式的處理

這個 skill 用在已經在開發中的專案，規則和全新專案不同：

- **已經驗證過、在使用中的程式不刪。** 「先寫的程式碼一律刪掉重來」只適用於這次對話裡、還沒有測試就寫出來的新程式。
- **既有程式沒有測試時，先寫「特徵測試」。** 拿一組已知的輸入跑現有程式，把目前的輸出記成期望值鎖住。它不判斷對錯，只確保之後的修改不會不小心改到既有行為。
- **碰到哪裡，才整理哪裡。** 不要一次把舊程式全部改成可測的形式；只在這次修改碰到的地方，順便搬出邏輯、補上測試。

## 不適用 TDD 的情況

以下情況直接照一般方式進行，並在開始時說一聲「這部分不走 TDD，原因是……」：

- **探索性分析**：還不知道答案、在找原因。探索完得出結論，要寫成正式程式時，再回到 TDD。
- **一次性、用完即丟的腳本或原型。**
- **測試環境測不到的部分**：例如畫面外觀、試算表底色與粗體。改完要列出「需要人工實測的項目」交給使用者。
- **文件、設定檔、資料檔的內容、自動產生的程式碼。**
- 專案說明列為不走 TDD 的其他改動。

其他任何想跳過的情況，先問使用者。

## 測試寫法

- **一條測試抓一種錯。** 寫之前先回答：「程式怎麼改，這條測試會失敗？」答不出來，這條測試就沒價值。
- **不要寫「變更偵測器」。** `assert MAX_RETRIES == 5` 只在有人刻意改設計時失敗，真正的 bug 抓不到。改測依賴這個值的行為：「失敗時重試 5 次，第 6 次不會發生」。
- **測自己的程式，不測框架或函式庫。**
- **少用 mock，不要斷言 mock 本身。** mock 只用在慢的或外部的依賴（網路、試算表、硬體），而且模擬的資料結構要和真的一樣完整。**測試框架不能比真實環境寬鬆**，否則會通過真實環境做不到的操作，甚至製造假的 bug 報告。
- **只給測試用的程式放在測試工具裡**，不要加進正式程式碼。

## 收尾：突變檢查與回報

完成前，實際把剛寫的程式改壞，確認每一種改法都會讓至少一條測試失敗：
- 常數或參數改錯（`>=` 改成 `>`）
- 走錯分支
- 少了一個狀態變化或副作用
- 回傳空值或預設值
- 漏掉對零、空白、未授權、格式錯誤輸入的檢查

沒有任何測試失敗的改法，就是還沒被保護到的地方，要補測試或在回報中列出。

最後給使用者的回報包含：
1. 新增了哪些測試（名稱列表），每條是否都先看過失敗。
2. 全部測試結果，和基準線比對（例如「基準 136/136 → 現在 140/140」）。任何失敗都要點名，包括不是這次造成的。
3. 突變檢查發現的未保護之處（如果有）。
4. 需要人工實測的項目（畫面、格式、實機）。

## 安全界線

- **不推送到正式分支、不部署。** 例如推到 main 就會更新正式網站、把程式貼進正式後端就會影響正式資料。改完推到開發分支、開 PR，由使用者決定何時 merge 與部署。
- 不修改正式資料或正式設定；測試一律用專案提供的假資料或模擬環境。
