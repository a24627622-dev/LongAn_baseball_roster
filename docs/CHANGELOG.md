## 網站整體方針(2026-09-20 拷問定案)

**對外／對內切分**,同一個 repo 不同資料夾:

- **對外**(`/`):公告、賽事時程 & 練球、球員名單(球員卡)、賽事成績。資料放 repo 的靜態 JSON(`data/*.json`),不直接打 GAS。響應式版面,手機單欄、桌機最大約 960px。**目標 2026-10-15 上線**。
- **對內**(`/tools/`):陣容調度、成績登記、照片上傳。維持 480px 手機容器。進入頁面需通過 `Auth.gs` 的 GAS 登入。

**為什麼對外不打 GAS**:GAS Web App 冷啟動 1~3 秒、沒有 CDN、併發與配額壓在個人帳號上。實測 `getGameLineup` 一次請求 **2172 毫秒**。靜態 JSON 走 GitHub Pages 的 CDN,零延遲零配額,GAS 掛掉也不影響對外網站。

**資料流方向**:試算表(唯一真實來源)→ GAS 匯出 JSON → commit 進 repo → 對外頁面讀靜態檔。

**已確認的事實**:試算表目前只有「球員名單」「調度紀錄」兩個常設分頁 + 各賽事分頁,**沒有時程或公告分頁**。所以公告與賽事時程第一版是純手維護 JSON,10/15 那批完全不需要動 GAS。

**維護方式**:公告與時程的 JSON 由使用者在對話中口述、Claude 修改並 commit。不做後台編輯頁。

**品牌色**(已定義於 `style.css`,對外沿用):深紅 `#b91c1c`、勁黑 `#111827`、橘紅 `#ea580c`、冠軍金 `#d97706`。

**10/15 驗收標準**:手機打開網址,首頁／公告／時程三頁都是真資料、不需橫向捲動、載入 1 秒內。

**狀態**:已部署上線並在真實試算表驗證完成。

### 規則依據(MLB Rule 5.11(a))

| 條款 | 內容 |
|---|---|
| (4) | 被換下的 DH 不得以任何身分重返比賽 |
| (5) | DH 上場守備時**棒次不變**,但**投手必須接替「被換下的守備球員」的棒次**;多重換人時由教練指定棒次 |

| (12) | DH 上場守備 → DH 終止 |

### 修正一:`lineup.html` — DH 取消後投手選不到(真實缺陷)

`subCandidates` 原本的條件是 `hasDHInLineup && !isDHCancelled && activePitchers.length > 0`。但「DH 去守備」**本身就會讓 `isDHCancelled` 變 true**,於是 (5) 要求的下一步「投手接替被換下者的棒次」在 UI 上做不到——現任投手既不在板凳名單(他已上場),也不再被加回候選名單。打線卡在缺投手的非法狀態,無解。

反過來的順序(先把投手放進打序、再讓 DH 去守備)可以繞過,但那不是記錄員在場邊會想到的順序。

**修法**:改成只要該投手**尚未進入打序**就保留在候選名單,與 `isDHCancelled` 無關。

**為什麼一直沒被發現**:既有的 28 項裡本來就有一案寫的正是正確序列(連「守備完整」都斷言了),但測試框架的 `sub()` 直接塞 player id、繞過了候選名單,所以它一直是綠的。修好框架的保真度之後,這一案立刻轉紅,缺陷才浮出來。

### 修正二:`lineup.html` — 守位重複時擋住調度上傳

步驟三的上傳按鈕先前不受 `activeDefenseNotice` 約束(只顯示紅字)。現在 `conflicts` 非空時 disable 按鈕並顯示「⚠️ 守位重複無法上傳」,函式本身再擋一層並跳出說明。

**`missing` 不擋**:代打／代跑之後守備還沒輪到,那是合法的中間狀態,擋了會讓記錄員在比賽中無法即時記錄代打。工具的 `conflicts` / `missing` 本來就分開,這個區分是對的。

### 修正三:`gas/Code.gs` — 純守位變更列的打擊成績填「-」

同一位球員在同一棒次換守位時(例如 3B→P、DH→RF),打者表會產生兩列。依使用者定案的呈現方式,第二列是**守位變更紀錄**,不是另一筆打擊紀錄:

```
2  3B (5)   黃三      先發   AB 3  H 2  …   公式 公式 公式 公式   ← 打擊成績記這裡
2  P (1)    ↳ 黃三    替補   -  -  -  …     -    -    -    -      ← 守位變更
```

**通則**:每個「棒次＋球員」組合,第一列帶成績,之後同一人的列都填「-」。投球成績本來就另外記在投手表。真正的換人(不同球員)不受影響。

**實作細節**:率值欄寫字串而非公式——若 AB 欄是文字「-」,Sheets 的 `"-" > 0` 會判定為 TRUE,公式會算出無意義的值。成績合計的 SUM 會自動忽略文字,總數不受影響。

### 修正四:`gas/Code.gs` — 成績保留的比對 key 會碰撞(隱藏 bug)

`savedStats` 的 key 是「打順｜姓名｜角色」。在**替補球員自己換守位**時兩列同 key(例如都是 `1|↳ 謝替|替補`),讀取時後者覆蓋前者;加上「-」之後,重寫會把該球員真正的成績換成「-」而**永久消失**。

(黃三那種情況不會中,因為 `黃三|先發` 和 `↳ 黃三|替補` 名字不同。)

**修法**:key 再帶上「第幾次出現」。這個 bug 在加「-」之前就存在,只是沒有「-」時兩列內容一樣,看不出來。

### 修正五:`tests/harness.js` — 測試框架保真度

`sub()` 原本直接塞 player id,可以做出真實 UI 做不到的操作(例如選到已退場的球員)。改成先驗證該球員存在於 `subCandidates`,否則丟出錯誤並列出目前候選。

**教訓**:測試框架如果比真實 UI 寬鬆,不只會讓測試失去意義,還會製造出假的 bug 報告。此前回報的「`willCancelDH` 與 `isDHCancelled` 判定不一致」就是這樣產生的錯誤結論,已收回——`isCurrentDHPitcher` 的判定正確且足夠。

1. V01.00.01 的 `writeBatterBlock` 沿用了使用者最初貼出的 GAS 原始碼裡的**18欄舊格式**(A~R,到 OPS 為止)。但 `2026-08-30_G4_雨人` 這場的試算表,實際上已經被手動升級成**21欄新格式**(多了獨立的 SLG 欄,以及「調度上傳時間」「成績上傳時間」兩欄)——這正是之前討論「box score 完整版」時看到的目標格式。
2. 上一版邏輯是「原地清除舊資料範圍、重新寫入」,沒有考慮到資料列數量可能變多或變少。這次調度多了一列,新資料的最後一列就直接蓋到了原本「成績合計」那一列的位置上,把它覆寫掉了。

**修法**:
1. 正式把 21 欄新格式(AVG/OBP/SLG/OPS + 調度上傳時間 + 成績上傳時間)訂為所有比賽分頁的標準格式,往後新建立的比賽分頁都會直接是這個完整格式。
2. 改用「插入 / 刪除列」取代「原地覆寫」:資料列數量變動時,下方內容(成績合計列、之後的投手表等)都會正確跟著往下或往上位移,不會再被蓋掉或錯位。
3. 「成績合計」改成程式自動維護的 SUM 公式列,不再是手動輸入、容易被沖散的固定列,每次調度更新都會自動重新計算、重新定位。
4. 加了表頭自我修復機制:每次寫入前檢查表頭是不是完整的 21 欄格式,不是的話自動補齊,避免同類欄位對不齊的問題在其他分頁重演。
5. AB~SB 手動填的成績、成績上傳時間欄位,依然依「打順+姓名+角色」比對保留,不會被清空。

**驗證**:除了語法檢查,另外寫了一個模擬 Google 試算表讀寫行為的測試腳本,完整重現這次回報的真實案例(15列資料→追加1列變16列→寫入),逐項比對:資料列數是否正確、#49 蘇辰雄的兩筆替補紀錄是否都還在、成績合計列是否正確重新定位且公式範圍正確、下方其他內容是否正確跟著位移、既有手動成績是否有被保留——全部通過。

**已跑掉資料的復原方式**:部署後若瀏覽器分頁還開著(草稿還在),直接再按一次「更換確認並上傳」即可用瀏覽器裡完整的資料正確重寫回去;若分頁已關閉,需手動補回 #49 蘇辰雄那兩列再重新上傳一次。

## V01.00.01 — 2026-09-14

**修改檔案**:`lineup.html`、GAS `Code.gs`(後端)

**這次改了什麼**:

1. **修復「☁️ 回讀雲端歷史紀錄」按鈕(原本完全沒作用)**
   - 後端 `doPost` 原本沒有處理 `action === 'getGameLineup'`,前端送出後只會落到最下面「同步成功」的通用回應,沒有真的回傳任何資料;前端又只在 `res.mode==='json' && res.data` 都存在時才嘗試讀 `res.data.lineup`,兩邊格式也對不上(前端送 `gameId` 字串,後端要的是 `gameInfo` 物件)。
   - 新增 `getGameLineup` 分支:依 `gameInfo`(日期/場次/對手)找到對應分頁,讀出目前已寫入的先發＋替補資料,轉換成前端要的 `activeLineup` 結構回傳。

2. **修復「比賽中調度更換」實際上傳沒有真的寫入試算表的問題(額外發現的既有 bug)**
   - 前端 `uploadSubstitutionsToGAS` 送出的欄位其實是完整的 `activeLineup`(每個打序的 `{starter, substitutes[]}`),但後端舊版程式碼讀的是 `data.substitutions`／`data.changes`,兩者永遠是 `undefined`,迴圈跑 0 次——等於**每次點「更換確認並上傳」,畫面顯示成功,但試算表完全沒有寫入任何替補紀錄**。
   - 後端新增 `writeBatterBlock` 共用函式:收到完整 `activeLineup` 後,整段覆寫重建該分頁的打者資料區塊(不是逐筆附加),這樣不管上傳幾次、有沒有解鎖重編,試算表內容永遠跟畫面上最新狀態一致,不會重複也不會遺漏;同時會盡量比對「打順+姓名+角色」保留舊資料列裡已經手動輸入的 AB~SB 成績,避免調度更新後成績被清空。
   - `saveStarters` 也一併改用同一套 `writeBatterBlock`,順便修掉「不小心點兩次上傳先發,會產生重複列」的小問題。

3. **小修**:`doGet` 補上 try/catch,「球員名單」分頁欄位有誤時會回傳清楚的錯誤訊息,不會讓前端 fetch 直接失敗、整份名單讀不到。
