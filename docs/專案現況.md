| 不做 | 二刀流規則（5.11(b)）、「先發 DH 至少打一次」檢查 |

## 6. 對外官網規格（已實作）

### 6.1 三頁

| 路徑 | 內容 |
|---|---|
| `/index.html` | 本週／下次活動（大版位）＋下一場比賽小卡＋最新 3 則公告＋分頁入口 |

| `/schedule.html` | 未來依月份分組放上方，已結束的收進摺疊區 |

### 6.2 球隊活動慣例

- 活動固定在**週日**。有比賽就不練球，沒比賽就練球 08:00～12:00
- 練球 `08:00` 是**開始時間**，不是集合時間
- 比賽**一律開賽前一小時集合**，但 `gatherTime` 仍存進 JSON，保留例外的彈性
- 大漢聯盟賽程**約兩個月前才公布**，所以先把沒比賽的週日全排成練球，賽程公布後再改成 `game`

### 6.3 首頁大版位的行為

- 顯示第一個「日期 >= 今天且未取消」的活動，比賽和練球都可能佔據這個位置
- 落在本週（到本週日為止）時標題寫「本週活動」，已跨到下週時寫「下次活動」
- 比賽用深黑底＋紅邊＋大字；練球用白底＋金邊
- 旁邊固定一張「下一場比賽」小卡；如果大版位已經是那場比賽，就不重複顯示
- 活動當天顯示到午夜，隔天自動換成下一個

### 6.4 品牌色

品牌色只有一份，在根目錄的 `brand.css`，`site.css`（對外）與 `style.css`（對內）都 `@import` 它，**改色只改 `brand.css`**（2026-09-26 階段 B 合併）。


  不連外部網站、不連工具頁。填錯只警告、不顯示按鈕。公告產生器可以從下拉選單選比賽

- `body` 用 `\n` 換行，前端會渲染成段落
- `pinned: true` 會排在最前面
- **不做分類、不做標籤**

### 7.2 `data/schedule.json`

陣列，依 `date` 排序：

```json
[
  {
    "type": "game",
    "date": "2026-10-25",
    "gatherTime": "09:00",
    "startTime": "10:00",
    "venue": "大漢B球場",
    "opponent": "ZERO",
    "score": null,
    "resultUrl": null,
    "cancelled": false,
    "note": ""
  },
  {
    "type": "practice",
    "date": "2026-11-08",
    "startTime": "08:00",
    "endTime": "12:00",
    "venue": "",
    "cancelled": false,
    "note": ""
  }
]
```

規則：
- `type` 只能是 `game` 或 `practice`
- **不存星期和 `status`**，由前端從 `date` 計算，避免資料自相矛盾
- `cancelled`：取消是外部事實，無法從日期推導，所以要存。時程頁會顯示灰底刪除線＋紅色「已取消」，首頁大版位會自動跳過
- **改期** = 原本那筆標成 `cancelled: true`，另外新增一筆新日期，再發一則公告說明
- `venue` 留空 → 前端顯示「地點未定，請留意公告」
- `score` 比完手動填 `{ "longan": 7, "opponent": 3 }`，時程頁會自動判斷勝／敗／和並上色
- **`resultUrl`**：`null`，或 `"game.html?id=比賽ID"`（2026-09-29 起，V01.06.00）。有值時時程頁顯示「賽事成績 ➔」連結（V01.07.00 起的文字）。
  用時程編輯器比賽欄位的「文字轉播」填比賽 ID 即可，不用手寫；格式不對時自動檢查會警告、時程頁不顯示連結

### 7.3 內容維護方式

三條路並存：口述給 Claude、在 GitHub 網頁直接編輯、使用 `/tools/` 的兩個產生器（**推薦**）。
產生器的用法是「填好 → 產生整份檔案內容 → 複製 → 貼到 GitHub 編輯框（全選刪掉舊的再貼上）→ Commit」。
**產生器不會寫入任何資料**，所以不需要登入，也沒有金鑰外洩的風險。這是刻意的設計。
不管用哪條路改，`data/*.json` 一變動 GitHub 就會自動檢查格式，壞了會寄 email（第 4B 節）。

## 12. 給接手者的注意事項

### 12.1 環境

- **開工前一定先 `git pull --rebase origin main`**。判斷線上內容時，最可信的是 `git show <commit>:data/schedule.json`
- git 有時會留下 `.git/index.lock` 導致 pull 失敗，刪掉這個檔案即可
- **GAS 部署的是固定版本 25**。改了 `gas/*.gs` 一定要建立新版本才會生效
- 分支：Claude 推 `claude/…` 分支並開 PR，使用者在 GitHub 網頁 Merge（`DEVELOPMENT.md` 第 11 節）；`main` = 正式上線。舊的 `dev` 分支已停用，2026-09-29 刪除

### 12.2 使用者的工作方式

- **動手前先問清楚需求（grill-me／拷問）**：問題要編號、一題只問一件事，每輪約 5～8 題，每題附上建議答案
- 問完後先整理「規格」給使用者確認，確認後才開工；定案內容要記錄到文件裡

### 12.3 從前幾輪帶走的教訓

1. **每完成一個可交付項目，就回頭對照第 1～3 節的優先序**，再決定下一步
2. **新發現的問題寫進待辦，不要當場動手**，除非它擋住了當前的工作
3. **估時翻倍就停下來回報**
4. 對話變長時主動提議換新對話，並更新這份文件
5. 測試框架不能比真實 UI 寬鬆，否則會產生假的 bug 報告（見測試報告第九節）
